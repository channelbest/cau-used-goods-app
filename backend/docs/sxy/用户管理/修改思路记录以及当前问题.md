# 用户管理阶段开发说明

## 1. 文档目的

本文档说明用户管理模块已经确定的目标业务规则、当前实现情况、尚未完成的用户管理工作，以及需要其他模块配合修改的内容。

本文档中的内容分为三类：

- **已确定业务规则**：后续实现和联调应遵守的最终规则。
- **当前已实现**：现有后端代码已经提供的能力。
- **待完成或建议修改**：现有代码尚未满足，需要后续开发。

用户管理模块的核心职责是管理用户档案、学生认证、账号生命周期、角色权限和用户关联业务记录。举报、申诉、商品、订单等模块可以触发或配合用户状态变化，但不能各自定义不同的用户状态规则。

---

## 2. 模块边界

### 2.1 用户管理模块负责

- 查询用户基础档案、认证状态、账号状态和角色。
- 维护统一的账号状态流转规则。
- 校验谁可以修改用户状态和角色。
- 执行账号状态变化。
- 设置与账号状态对应的 `is_deleted`。
- 调用商品、订单等模块提供的业务方法，协调必要副作用。
- 记录管理员对用户执行的关键操作。
- 聚合用户关联商品、订单、举报、申诉、评价和管理员操作日志。

### 2.2 举报和申诉模块负责

- 举报模块负责判断举报是否成立、记录处理结果和处理说明。
- 申诉模块负责判断申诉是否成立、记录处理结果和处理说明。
- 举报和申诉模块不得直接更新 `users.account_status`。
- 需要处罚或恢复用户时，管理员应调用用户管理接口，并通过可选 `relatedType/relatedId` 关联举报或申诉来源。

### 2.3 商品和订单模块负责

- 商品模块负责商品状态变化、批量下架用户在售商品，以及商品状态变更对应的事务日志。
- 订单模块负责订单状态变化、管理员异常关闭订单，以及订单状态和商品状态联动的事务一致性。
- 用户管理模块可以协调用户状态变化的必要副作用，但必须通过商品、订单等模块暴露的业务方法完成，不在用户模块里手写商品或订单表 SQL。

推荐边界：

```text
举报/申诉模块：记录案件结论。
用户管理模块：决定用户状态能否变化、由谁操作，以及需要协调哪些副作用。
商品/订单模块：执行本模块内部的状态变化。
relatedType/relatedId：在具体处置日志中记录处置依据。
```

## 3. 用户状态模型

用户状态由三个相互独立但有关联的字段表达：

| 字段 | 作用 |
| --- | --- |
| `auth_status` | 表示学生认证生命周期。 |
| `account_status` | 表示账号业务生命周期。 |
| `is_deleted` | 表示用户是否退出普通业务视图，用于普通业务查询过滤。 |

### 3.1 学生认证状态 `auth_status`

| 状态 | 含义 | 规则 |
| --- | --- | --- |
| `UNVERIFIED` | 未认证 | 可以提交学生认证。 |
| `PENDING` | 待审核 | 管理员可以审核为 `VERIFIED` 或 `REJECTED`。 |
| `VERIFIED` | 已认证 | 账号正常时可以使用核心交易功能。 |
| `REJECTED` | 认证失败 | 可以重新提交学生认证。 |

认证状态流转：

```text
UNVERIFIED / REJECTED -> PENDING
PENDING -> VERIFIED
PENDING -> REJECTED
```

### 3.2 账号状态 `account_status`

用户账号状态最终确定为：

```text
NORMAL / DISABLED / BANNED / CANCELED
```

不再使用用户账号状态 `DELETED`。永久封禁使用 `BANNED`，用户主动注销使用 `CANCELED`。

| 状态 | 含义 | 登录与使用规则 | 恢复规则 |
| --- | --- | --- | --- |
| `NORMAL` | 正常账号 | 可以正常登录；通过学生认证后可以使用核心交易功能。 | 无需恢复。 |
| `DISABLED` | 临时禁用 | 可以进入受限页面、查看处罚原因、历史记录、系统消息并提交申诉；禁止核心业务操作。 | `ADMIN` 或 `SUPER_ADMIN` 可以恢复普通用户。 |
| `BANNED` | 永久封禁 | 可以进入受限页面、查看处罚原因、历史记录、系统消息并提交申诉；禁止核心业务操作；公开资料不可查看。 | 原则上不恢复；申诉通过后仅 `SUPER_ADMIN` 可以恢复。 |
| `CANCELED` | 用户主动注销 | 不签发正常登录凭证，不参与普通业务，不接收新的系统消息，公开资料不可查看。 | 用户通过微信身份重新确认后可以重新激活。 |

核心业务操作包括但不限于：

- 发布、编辑、上下架和删除商品。
- 创建、确认、完成或主动取消订单。
- 收藏、评价和举报。
- 创建聊天会话和发送聊天消息。
- 修改用户资料和再次提交学生认证。

### 3.3 `account_status` 与 `is_deleted`

`account_status` 表达账号为什么可用、受限或退出；`is_deleted` 负责将已注销用户排除出普通业务查询。

确定的不变量：

| `account_status` | `is_deleted` |
| --- | ---: |
| `NORMAL` | `0` |
| `DISABLED` | `0` |
| `BANNED` | `0` |
| `CANCELED` | `1` |

说明：

- `DISABLED` 和 `BANNED` 用户仍然是平台账号，需要保留处罚、通知和申诉能力，因此不能设置 `is_deleted=1`。
- `CANCELED` 用户已主动退出平台，普通业务查询应通过 `is_deleted=0` 将其过滤。
- 管理员用户管理查询必须能够查看 `is_deleted=1` 的注销用户。
- 登录查询属于特殊查询，必须按 `openid` 查询包括 `CANCELED` 在内的用户，不能只查询 `is_deleted=0`。
- 当前不执行隐私匿名化。注销用户原始资料仍保存在数据库中，仅对普通用户隐藏，管理员后台仍可追溯。

### 3.4 用户状态流转

确定的状态流转：

```text
NORMAL -> DISABLED
NORMAL -> BANNED
NORMAL -> CANCELED

DISABLED -> NORMAL
DISABLED -> BANNED

BANNED -> NORMAL
CANCELED -> NORMAL
```

具体权限和条件：

| 状态流转 | 操作人 | 条件 |
| --- | --- | --- |
| `NORMAL -> DISABLED` | `ADMIN` / `SUPER_ADMIN` | `ADMIN` 只能操作普通用户；`SUPER_ADMIN` 可以操作普通用户和普通管理员；必须填写原因。 |
| `NORMAL -> BANNED` | `ADMIN` / `SUPER_ADMIN` | `ADMIN` 可以永久封禁普通用户；`SUPER_ADMIN` 可以操作普通用户和普通管理员；必须填写原因。 |
| `DISABLED -> NORMAL` | `ADMIN` / `SUPER_ADMIN` | `ADMIN` 只能恢复普通用户；`SUPER_ADMIN` 可以恢复普通用户和普通管理员；必须填写原因。 |
| `DISABLED -> BANNED` | `ADMIN` / `SUPER_ADMIN` | `ADMIN` 只能操作普通用户；`SUPER_ADMIN` 可以操作普通用户和普通管理员；必须填写原因。 |
| `BANNED -> NORMAL` | 仅 `SUPER_ADMIN` | 仅在申诉通过等特殊场景执行，必须填写原因。 |
| `NORMAL -> CANCELED` | 用户本人 | 必须满足注销前置条件并二次确认。 |
| `CANCELED -> NORMAL` | 用户本人 | 必须重新验证同一微信身份并明确确认重新激活。 |

禁止的状态操作：

- 管理员不能修改自己的账号状态。
- 普通管理员不能修改其他管理员或超级管理员的账号状态。
- 超级管理员可以修改普通管理员的账号状态，但不能修改自己的账号状态。
- `CANCELED` 用户不能由普通管理员改为 `DISABLED` 或 `BANNED`。
- 账号状态不允许通过任意目标状态自由切换，只允许上述明确流转。

### 3.5 状态变化的业务副作用

#### 临时禁用 `DISABLED`

- 如果用户作为卖家或买家存在 `WAIT_MEET` 订单，禁用操作直接失败，并按角色返回明细错误提示给前端；此时不会修改用户状态、不会异常关闭订单，也不会下架商品。
- 如果用户作为卖家或买家只存在 `PENDING_CONFIRM` 订单，禁用操作可以继续，系统会在同一事务内自动将这些待确认订单改为 `EXCEPTION_CLOSED`。
- 自动异常关闭待确认订单时：被禁用用户是买家则商品恢复为 `ON_SALE`；被禁用用户是卖家则相关锁定商品下架。
- 自动下架该用户所有 `ON_SALE` 商品。
- 待确认订单异常关闭、相关商品状态处理、用户在售商品下架、用户状态变更和管理员日志写入处于同一事务。
- 如果禁用请求携带 `relatedType/relatedId`，自动异常关闭订单日志和自动下架商品日志也会携带同一组关联来源。
- 事务提交后发送系统消息：受影响订单的买卖双方收到订单异常关闭消息，被禁用用户收到账号状态变更消息；消息通知失败不回滚主业务。
- 禁止用户继续执行订单、商品、评价、举报和聊天等核心操作。
- 允许接收系统消息和提交申诉。

#### 永久封禁 `BANNED`

- 如果用户作为卖家或买家存在 `WAIT_MEET` 订单，封禁操作直接失败，并按角色返回明细错误提示给前端；此时不会修改用户状态、不会异常关闭订单，也不会下架商品。
- 如果用户作为卖家或买家只存在 `PENDING_CONFIRM` 订单，封禁操作可以继续，系统会在同一事务内自动将这些待确认订单改为 `EXCEPTION_CLOSED`。
- 自动异常关闭待确认订单时：被封禁用户是买家则商品恢复为 `ON_SALE`；被封禁用户是卖家则相关锁定商品下架。
- 自动下架该用户所有 `ON_SALE` 商品。
- 待确认订单异常关闭、相关商品状态处理、用户在售商品下架、用户状态变更和管理员日志写入处于同一事务。
- 如果封禁请求携带 `relatedType/relatedId`，自动异常关闭订单日志和自动下架商品日志也会携带同一组关联来源。
- 事务提交后发送系统消息：受影响订单的买卖双方收到订单异常关闭消息，被封禁用户收到账号状态变更消息；消息通知失败不回滚主业务。
- 禁止用户继续执行核心业务操作。
- 普通用户不能查看该用户公开资料。
- 允许用户查看处罚信息、接收系统消息和提交申诉。

#### 主动注销 `CANCELED`

- 只有 `role=USER` 的普通用户可以主动注销。
- `ADMIN` 必须先由 `SUPER_ADMIN` 降级为 `USER`，之后才能主动注销。
- `SUPER_ADMIN` 不能主动注销。
- 注销前必须不存在 `PENDING_CONFIRM` 或 `WAIT_MEET` 订单。
- 注销前要求用户二次确认。
- 自动下架该用户所有 `ON_SALE` 商品。
- 设置 `account_status=CANCELED`、`is_deleted=1`。
- 不再签发正常登录凭证，不再接收新的系统消息。
- 普通用户不能查看该用户资料。
- 历史订单、举报、申诉、评价和聊天记录继续保留。

#### 恢复和重新激活

- `DISABLED -> NORMAL`、`BANNED -> NORMAL` 和 `CANCELED -> NORMAL` 都不自动重新上架商品。
- 已关闭订单不恢复。
- 注销用户重新激活时继续使用原 `user_id`，不能创建新的用户记录。
- 注销用户重新激活后保留原学生认证状态，但角色强制恢复为 `USER`。
- `CANCELED -> NORMAL` 时同步设置 `is_deleted=0`。
- 当前不额外记录用户主动注销和重新激活历史。

## 4. 用户角色和管理权限

### 4.1 用户角色

| 角色 | 含义 |
| --- | --- |
| `USER` | 普通用户 |
| `ADMIN` | 普通管理员 |
| `SUPER_ADMIN` | 超级管理员 |

### 4.2 角色修改规则

- 只有 `SUPER_ADMIN` 可以修改用户角色。
- 超级管理员不能修改自己的角色。
- 只有 `account_status=NORMAL` 的用户才可以被修改角色。
- 修改角色不要求目标用户已经通过学生认证。
- 当前系统只有一个超级管理员，不设计复杂的多超级管理员互相管理流程。
- 由于超级管理员不能修改自己的角色，当前唯一超级管理员实际上不能被接口降级或移除。
- 角色变更必须填写原因并写入 `admin_logs`。

允许的角色流转：

```text
USER -> ADMIN
ADMIN -> USER
```

说明：当前系统按“唯一超级管理员”设计，不通过业务接口新增、降级或移除 `SUPER_ADMIN`。如需变更唯一超级管理员，应通过受控初始化或运维流程完成，而不是开放给普通后台接口。

### 4.3 普通管理员权限

普通管理员可以：

- 查询用户列表和用户详情。
- 审核学生认证。
- 临时禁用、恢复和永久封禁普通用户。
- 查看用户关联业务记录和管理员操作日志。
- 根据实际情况处理异常订单。

普通管理员不能：

- 修改用户角色。
- 修改自己、其他管理员或超级管理员的账号状态。
- 撤销永久封禁。
- 查看用户 `openid`。
- 查看管理员操作日志中的完整 IP 地址。

### 4.4 超级管理员权限

超级管理员额外可以：

- 修改用户角色。
- 管理普通管理员账号。
- 在申诉通过等特殊情况下执行 `BANNED -> NORMAL`。
- 查看用户 `openid`。
- 查看管理员操作日志中的完整 IP 地址。

所有后台接口都必须实时查询数据库校验：

```text
role = ADMIN 或 SUPER_ADMIN
account_status = NORMAL
is_deleted = 0
```

## 5. 用户资料展示与隐私规则

用户资料必须按使用场景返回，不能使用一个万能用户详情接口向所有角色返回相同字段。

### 5.1 当前用户查看本人资料

接口：

```http
GET /users/me
```

根据当前 `users` 表，可以返回：

```text
id、nickname、avatarUrl、studentId、realName、college、phone、
role、authStatus、accountStatus
```

用户可以查看自己的完整手机号、学号和真实姓名。

### 5.2 普通用户查看他人公开资料

目标接口：

```http
GET /users/:id/public
```

公开资料只允许返回现有字段中的：

```text
id、nickname、avatarUrl、authStatus
```

不返回：

```text
openid、studentId、realName、college、phone、role、
accountStatus、lastLoginTime、createTime、updateTime、isDeleted
```

公开资料状态规则：

| 目标用户状态 | 结果 |
| --- | --- |
| `NORMAL` | 返回公开资料。 |
| `DISABLED` | 可以返回公开资料，但前端应标记账号暂不可交易。 |
| `BANNED` | 不返回个人资料。 |
| `CANCELED` | 不返回个人资料。 |

历史订单、评价或聊天记录需要显示用户时：

```text
BANNED   -> 显示“违规账号”，不显示原昵称和头像。
CANCELED -> 显示“已注销用户”，不显示原昵称和头像。
```

### 5.3 管理员查看用户资料

普通管理员可以在用户管理场景查看：

```text
id、nickname、avatarUrl、studentId、realName、college、phone、
role、authStatus、accountStatus、lastLoginTime、createTime、
updateTime、isDeleted
```

普通管理员不能查看：

```text
openid、管理员操作日志中的完整 IP 地址
```

超级管理员在普通管理员字段基础上可以额外查看：

```text
openid、管理员操作日志中的完整 IP 地址
```

管理员用户列表默认显示：

```text
NORMAL / DISABLED / BANNED
```

注销用户默认不进入列表结果，需要通过：

```http
GET /admin/users?accountStatus=CANCELED
```

主动筛选。

## 6. 用户关联业务记录

管理员用户详情可以聚合并分页查询：

- 用户发布的商品。
- 用户作为买家或卖家参与的订单。
- 用户提交或作为对象的举报。
- 用户提交或作为对象的申诉。
- 用户发出或收到的评价。
- 管理员对该用户执行的操作日志。

### 6.1 用户存在与空列表

```text
用户存在但没有关联记录 -> HTTP 200，返回空列表和 total=0。
用户 ID 不存在         -> HTTP 404。
```

### 6.2 逻辑删除业务数据查询

商品和评价可能存在逻辑删除数据，管理员关联查询支持：

```text
dataScope=ACTIVE    默认，仅返回未逻辑删除数据。
dataScope=DELETED   仅返回逻辑删除数据。
dataScope=ALL       返回全部数据。
```

订单、举报、申诉和管理员日志属于审计和追溯记录，不因用户注销而隐藏。

## 10. 其他模块建议修改部分

### 10.1 登录认证模块

- `FindByOpenID` 登录查询不能过滤 `is_deleted=1`，否则无法识别注销用户。
- 微信登录发现 `CANCELED` 时不能创建新用户，也不能签发正常业务 token。
- 微信登录发现 `DISABLED` 或 `BANNED` 时，只允许进入受限页面和申诉流程。
- 增加注销用户重新激活入口。当前方案为：微信登录接口先用 `code` 换取 `openid` 并识别原注销账号，返回 `reactivationToken`；`/auth/reactivate` 校验该恢复凭证和用户确认后，调用用户管理服务执行 `CANCELED -> NORMAL`。
- JWT 认证中间件继续只负责验证 token 和识别用户身份，不负责决定账号当前可以执行哪些业务。
推荐职责

中间件	作用	典型接口
AuthJWT	验证身份，获取 userID	所有登录接口
RequireReadableAccount	允许 NORMAL / DISABLED / BANNED，阻止 CANCELED 旧 token	历史订单、消息、申诉
RequireNormalAccount	只允许 NORMAL	修改资料、上传头像、提交认证、主动注销
RequireVerifiedAccount	要求 NORMAL + VERIFIED	发布商品、创建订单、评价、举报、发送聊天
RequireAdmin	要求 NORMAL + ADMIN/SUPER_ADMIN	管理员接口
RequireSuperAdmin	要求 NORMAL + SUPER_ADMIN	角色修改、撤销永久封禁

### 10.2 商品模块

- 商品发布、编辑、上下架、删除和图片修改的业务授权条件为：

```text
auth_status=VERIFIED
account_status=NORMAL
```

- `is_deleted` 不作为独立的第三个业务授权条件。按照用户状态不变量，`account_status=NORMAL` 已经意味着 `is_deleted=0`。
- 商品模块底层查询仍可以使用 `is_deleted=0` 作为防御性过滤，避免状态数据异常时让已退出普通业务视图的用户进入写流程。
- 提供按用户批量下架所有 `ON_SALE` 商品的服务方法。
- 用户恢复或重新激活时不得自动上架历史商品。
- 因账号禁用/封禁自动下架的在售商品，`products.off_shelf_by` 写入 `ACCOUNT_STATUS`，与管理员直接下架 `ADMIN`、用户主动下架 `USER`、普通系统下架 `SYSTEM` 区分。
- 账号恢复后，`ACCOUNT_STATUS` 商品保留为 `OFF_SHELF`，由用户在“我的商品”中单个上架或一键上架；恢复时会清空 `off_shelf_by/off_shelf_reason`。
- 管理员直接下架或普通系统下架的商品不允许用户自行上架，卖家可通过商品详情页固定目标申诉入口提交 `PRODUCT` 申诉。

### 10.3 订单模块

- 管理员异常关闭订单使用 `POST /admin/orders/:id/exception-close`。
- 管理员异常关闭时必须填写原因和责任方 `BUYER / SELLER`、写入 `admin_logs` 并通知买卖双方；请求体可选 `relatedType/relatedId`，用于关联举报或申诉来源。
- 管理员修改订单状态使用 `PUT /admin/orders/:id/status`，请求体可选 `relatedType/relatedId`。
- `PUT /admin/orders/:id/status` 不允许直接设置 `EXCEPTION_CLOSED`；异常关闭必须走专门接口，避免缺少责任方导致商品恢复/下架规则不一致。
- 普通订单创建/取消/完成已保证订单状态和商品锁定/解锁/售出在同一事务内完成；消息通知在事务提交后发送，通知失败不回滚主业务。
- 超时未确认订单不再作为普通管理员接口处理，由服务端启动后台定时任务每 1 分钟清理一次。
- 定时任务使用数据库时间判断 `expire_time < NOW()`，并在取消订单时带上 `status='PENDING_CONFIRM'` 条件；只有 `RowsAffected=1` 的执行者才继续解锁商品和发送超时取消消息，避免并发或多实例部署时重复处理同一订单。
- 当前订单路由已区分只读和写操作权限：

```text
DISABLED / BANNED：
可以查看本人历史订单，不允许创建、确认、取消、完成或异常关闭订单。
```

- 管理员关闭因卖家异常导致的订单时，商品保持下架。
- 管理员关闭因买家异常导致的订单时，商品可以恢复为 `ON_SALE`。

### 10.4 举报和申诉模块

- `/admin/reports/:id/handle` 只负责将举报处理为 `APPROVED` 或 `REJECTED`，写入处理说明、管理员日志并通知举报人。
- `/admin/appeals/:id/handle` 只负责将申诉处理为 `APPROVED` 或 `REJECTED`，写入处理说明、管理员日志并通知申诉人。
- 举报或申诉处理接口不再接受 `accountStatus` 作为联动处置字段；如果传入非空 `accountStatus`，接口返回错误并提示改用用户状态接口。
- 举报成立后需要封禁用户、下架商品或关闭订单时，管理员应分别调用用户、商品、订单后台接口，并传入 `relatedType=REPORT, relatedId=举报ID`。
- 申诉通过后需要恢复用户或商品状态时，管理员应分别调用用户或商品后台接口，并传入 `relatedType=APPEAL, relatedId=申诉ID`。
- 撤销 `BANNED` 仍必须由超级管理员通过用户状态接口执行。

### 10.5 聊天模块

- `DISABLED`、`BANNED` 和 `CANCELED` 用户不能创建新会话或发送新消息。
- 历史聊天记录保留。
- 历史记录中注销用户显示“已注销用户”，永久封禁用户显示“违规账号”。

### 10.6 消息模块

- `DISABLED` 和 `BANNED` 用户可以接收系统消息。
- `CANCELED` 或 `is_deleted=1` 用户不再接收新的系统消息；当前消息创建使用数据库条件插入校验接收者账号状态，不满足条件时跳过写入。

### 10.7 评价及其他展示模块

- 普通用户查看历史评价、订单或聊天时，不展示 `BANNED` 和 `CANCELED` 用户的原昵称、头像和其他个人资料。
- 评价逻辑删除数据仅在管理员使用 `dataScope=DELETED / ALL` 时返回。

### 10.8 管理员审计日志模块

当前 `admin_logs` 已统一为管理员后台写操作审计日志。业务模块不再直接执行 `INSERT INTO admin_logs`，统一通过 `admin.Service.LogActionTx` 写入；保留非事务 `LogAction` 仅作为纯日志或后续非关键审计入口，当前不记录管理员登录、导出记录、访问审计。

- 所有管理员后台写操作统一通过管理员日志服务事务版本写入，不在各业务模块中散落手写 SQL。
- `operation_type` 采用稳定常量集中管理，命名保持一致，例如 `CREATE_CATEGORY`、`MARK_REPORT_PROCESSING`、`APPROVE_REPORT`、`REJECT_APPEAL`、`USER_BAN`、`UPDATE_ORDER_STATUS`。
- `target_type` 表示本次操作直接作用的业务对象，例如 `USER`、`PRODUCT`、`ORDER`、`NOTICE`、`WORD`、`CATEGORY`、`REPORT`、`APPEAL`。
- `related_type` 和 `related_id` 只表示本次操作的业务依据，例如“因举报封禁用户”应记录为 `target_type=USER`，`related_type=REPORT`。
- 举报和申诉处理日志已区分处理中、通过、驳回，不再用同一个操作类型覆盖多个动作。
- 管理员查询、列表、统计接口不写入 `admin_logs`；如后续需要访问审计，应另设访问日志。
- 关键后台写操作的业务变更和日志写入在同一事务中完成，日志写入失败时业务回滚；消息通知失败不阻断主业务。
- 分类管理已补充审计日志：`CREATE_CATEGORY`、`UPDATE_CATEGORY`、`STATUS_CATEGORY`、`DELETE_CATEGORY`。
- 超时订单清理已改为定时任务，不作为普通管理员接口记录；如后续增加手动补偿入口，手动触发应记录为管理员操作，定时任务执行应使用单独的系统任务日志。

### 10.9 跨模块处置总体思路

当前后台处置采用“模块内事务一致 + 可选关联来源”的方案，不引入举报/申诉工作流大事务。

- 单个后台写操作必须由所属模块完成，并在同一事务内写入 `admin_logs`。
- 跨模块处置拆成多个明确操作，例如先在商品接口下架商品，再在举报接口批准举报；或先批准申诉，再在用户接口恢复账号。
- `relatedType/relatedId` 只记录处置依据，不改变业务对象归属：

```text
因举报封禁用户：
target_type = USER
target_id = 被封禁用户 ID
related_type = REPORT
related_id = 举报 ID

因申诉恢复商品：
target_type = PRODUCT
target_id = 商品 ID
related_type = APPEAL
related_id = 申诉 ID
```

- 管理员自己巡查发现问题时，不传 `relatedType/relatedId`。
- 基于举报或申诉处置时，用户、商品、订单后台状态接口均可传 `relatedType/relatedId`。
- 基于举报/申诉封禁或禁用用户时，如果父操作传入了 `relatedType/relatedId`，系统自动异常关闭待确认订单日志和自动下架商品日志才会继承同一组关联来源；父操作未传时，子订单/商品日志不写 `related_type/related_id`。
- `relatedType` 仅允许 `REPORT` 或 `APPEAL`，并且必须和 `relatedId` 同时传或同时不传；直接调用用户、商品、订单处置接口时，会校验对应案件存在且目标对象匹配当前处置对象。
- 消息通知不纳入业务事务，事务提交后发送；通知失败不回滚状态变更和管理员日志。订单异常关闭消息关联具体订单，账号状态变更消息关联具体用户，不继承举报/申诉作为用户侧消息关联对象。
